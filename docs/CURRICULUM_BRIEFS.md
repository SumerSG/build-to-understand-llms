# Curriculum briefs (design notes per module)

These are the design briefs each module was written from. They fix the artifact, the threshold concept,
the step outline, the facts the concept must get right, and where the toy differs from production.
Authors may refine names and step boundaries but must keep the artifact and the honesty notes.

Conventions for all modules: JavaScript in the browser sandbox; import only `lib/...`; seeded RNG from
`lib/util.js`; a starter with at least one worked example; 3–6 steps; exactly 3 hints per step; `recall`
questions about earlier modules and `review` questions about this one; demo with at least one visual and
`lab.done` with real numbers; all tests < 10 s and demo < 60 s in Node on the solution.

## 02-autograd — Autograd from scratch
**Artifact.** A reverse-mode autodiff engine over raw tensors: a `Tensor` class with `add`, `mul`, `matmul`, `sum`, `mean`, `exp`, `log`, `relu`, a fused `crossEntropy`, `backward()`; `gradCheck`; SGD training of `y = 3x + 2` from noisy data.
**Threshold concept.** A computation graph records how each value was made; the chain rule run backwards over that record gives every gradient at the cost of about one extra forward pass.
**Build (steps).** (1) The `Tensor` wrapper and a topological sort of the graph. (2) Backward for `add`/`mul` with broadcasting (`unbroadcast` = sum over broadcast dims). (3) Backward for `matmul` (`dA = dC·Bᵀ`, `dB = Aᵀ·dC`) and `sum`/`mean`. (4) Nonlinearities and the fused `crossEntropy(logits, targets)` whose gradient is `softmax − onehot` divided by N. (5) `gradCheck` with central differences (eps 1e-3, tol 1e-2 in float32) and a linear-regression training loop with `SGD`.
**Concept must cover.** Forward vs reverse mode and why reverse suits "many params, one loss"; the `_backward` closure pattern (micrograd); gradient accumulation (`+=`) when a tensor is used twice; why `zeroGrad` exists; float32 numerical-check tolerances.
**Starter scaffolding.** Forward ops fully implemented using `lib/ops.js`; `add`'s backward fully worked; `mul` half done; the rest TODO.
**Demo.** Train linear regression for 200 steps, plot loss, print learned `w, b` near 3 and 2; gradCheck table on a small MLP.
**Real systems.** PyTorch autograd, JAX `grad`; mention that frameworks fuse softmax+CE for stability exactly as this module does.
**Honesty.** No graph freeing, no in-place ops, scalar-loss only.
**Lib.** Solution mirrors `lib/tensor.js`; imports `lib/ops.js`, `lib/util.js`.

## 03-tokenizer — A BPE tokenizer
**Artifact.** `BPETokenizer` with `train(text, {vocabSize})`, `encode`, `decode`, pre-tokenisation regex, special tokens; exact round-trip; compression-ratio plot vs vocab size.
**Threshold concept.** A tokenizer is a learned, lossless compression scheme: it greedily merges the most frequent adjacent pair until the vocabulary is full, trading sequence length for vocabulary size.
**Steps.** (1) Pre-tokenise with the GPT-2-style regex (words, numbers, punctuation, whitespace). (2) Count adjacent pairs across all pre-tokens (a `Map` keyed by a joined pair string with a separator that cannot occur in the text). (3) The merge loop: pick the most frequent pair (ties by first-seen order), replace, record the merge, repeat until `vocabSize`. (4) `encode`: apply merges in learned order; `decode`: concatenate; special tokens matched first. (5) Round-trip and compression metrics (`bytes / tokens`).
**Concept must cover.** Why not characters (long sequences) or words (OOV, Zipf tail from module 00); byte-level BPE in GPT-2 vs char-level here; vocab sizes (GPT-2 50,257; Llama 3 128,256); the "tokenizer decides what the model can count" pathology (digits, spaces); SentencePiece/Unigram as the alternative.
**Demo.** Train on `CORPUS` for vocab 128/256/512, plot tokens-per-character vs vocab, show the first 20 merges, encode/decode a sentence and highlight token boundaries in a table.
**Honesty.** Char-level base vocab from the corpus (real BPE uses 256 bytes so nothing is OOV); no regex-based Unicode categories; O(n) merge loop rather than the priority-queue implementations in `tiktoken`.
**Lib.** Solution mirrors `lib/tokenizer.js`; imports `lib/data.js` (CORPUS), `lib/util.js`.

## 04-bigram — From counting to learning: the bigram model
**Artifact.** A count-based bigram model (with add-alpha smoothing) and a neural bigram model (embedding table = logits, trained with cross-entropy via `lib/tensor.js`), both evaluated by perplexity and sampled from.
**Threshold concept.** A language model is a conditional probability table over the next token; "training" replaces counting with gradient descent on the same objective (cross-entropy = negative log-likelihood), which is what lets it generalise when the table is too big to count.
**Steps.** (1) Count bigrams into a `[V, V]` table; normalise rows with add-alpha smoothing. (2) Negative log-likelihood and perplexity on held-out text; show that alpha=0 gives infinite perplexity. (3) Sampling from a row with a seeded RNG (temperature). (4) The neural bigram: `logits = W[x]` (an embedding lookup), loss = `crossEntropy`, SGD/AdamW for N steps. (5) Compare: the neural model converges to (about) the counts; perplexity curve.
**Concept must cover.** Maximum likelihood = counting; why perplexity is exp(mean NLL) and what "perplexity 20" means (as-if choosing among 20 equally likely tokens); smoothing as a prior; the equivalence between the trained neural bigram and the count table; why the neural version matters (it generalises to contexts you cannot count, which is where module 05 goes).
**Demo.** Train both on the char-level corpus; plot neural loss vs steps with the count model's NLL as a horizontal reference; sample 200 characters from each; table of perplexities.
**Real systems.** Karpathy's makemore; n-gram LMs (Kneser–Ney) that ruled before 2012; mention that GPT's output layer is exactly "logits = h · Wᵀ" generalising `W[x]`.
**Lib.** `lib/tokenizer.js` (`CharTokenizer`), `lib/data.js`, `lib/tensor.js`, `lib/optim.js`, `lib/util.js`.

## 05-attention — Attention from scratch
**Artifact.** `attention(q, k, v, {causal})` returning `{out, weights}` on `Tensor`s, plus `MultiHeadAttention` (qkv projection, head split/merge with `reshape`/`permute`, output projection); heatmap of the weights.
**Threshold concept.** Attention lets each position build its representation as a weighted average of other positions' values, with weights computed from query–key similarity; the causal mask is what makes it a language model.
**Steps.** (1) Scores `q·kᵀ / sqrt(dh)` and why the scale (variance of a dot product of d independent unit-variance terms is d). (2) Causal mask with `-Infinity` before softmax, and the softmax itself. (3) Weighted sum with `v`; shapes `[B,H,T,dh]`. (4) Multi-head: split `[B,T,C]` into `[B,H,T,dh]`, run attention, merge back; output projection. (5) A test that the output at position t does not change when tokens after t change (causality), and a gradient check through the layer.
**Concept must cover.** Q/K/V intuition without hand-waving (a soft dictionary lookup); why multiple heads; parameter count `4·C²`; FLOPs `O(T²·C)` per layer and why long context is expensive (sets up KV cache and FlashAttention); the mask as an upper-triangular `-inf`; that GPT-2 uses exactly this with `C=768, H=12`.
**Demo.** Run the learner's MHA on a short token sequence with the pre-trained checkpoint's first block weights loaded via `lib/infer.js` (or on random weights if simpler); draw the `[T,T]` heatmap per head (rowLabels = tokens); verify causality numerically; report the attention entropy per head.
**Honesty.** No FlashAttention tiling, no RoPE (GPT-2-style learned positions live in module 06), no GQA.
**Lib.** `lib/tensor.js`, `lib/ops.js`, `lib/util.js`, optionally `lib/checkpoints/tiny-gpt.json` via `lib/infer.js`.

## 06-transformer — The GPT architecture
**Artifact.** `Linear`, `Embedding`, `LayerNorm`, `MLP`, `Block`, `GPT` on `lib/tensor.js`, forward pass to logits `[B,T,V]`, `numParams()`, and a `countParams(config)` formula that matches the built model exactly.
**Threshold concept.** A GPT is a stack of identical residual blocks that alternately mix information across positions (attention) and transform each position independently (MLP); everything else is plumbing.
**Steps.** (1) `Linear` and `Embedding` layers with init `std=0.02`. (2) Token + position embeddings, `blockSize`. (3) The pre-LN block: `x + attn(ln1(x))`, `x + mlp(ln2(x))` with `gelu` and 4× hidden. (4) Stacking, final LayerNorm, tied LM head (`logits = x · wteᵀ`). (5) `countParams(config)` closed form (`12·L·C² + V·C + T·C + ...`) and a test that it equals `numParams()` for three configs; a shape test on the forward pass.
**Concept must cover.** Residual stream as the "highway"; pre-LN vs post-LN and why pre-LN trains stably; parameter budget breakdown (attention 4C², MLP 8C² per block; 12LC² total); where the parameters of GPT-2 small (124M) and Llama-3-8B go (make the arithmetic explicit); weight tying; differences in Llama (RMSNorm, SwiGLU, RoPE, no biases) mentioned in one paragraph.
**Demo.** Build the lab config (vocab 256, block 64, 2 layers, 4 heads, 64 dims), print the parameter table by component (bar chart), run a forward pass on random tokens and show the logits row for the last position as a bar chart of top-10 tokens, and report FLOPs per token = 2·params (+ attention term).
**Lib.** `lib/attention.js` (reference MHA is allowed as an import in the starter, since module 05 built it), `lib/tensor.js`, `lib/ops.js`.

## 07-pretraining — The pre-training loop
**Artifact.** A training loop: `getBatch`, loss, `AdamW`, warmup+cosine schedule, gradient clipping, periodic validation, sampling; trains a small GPT in the browser until samples look like the corpus; loss curve.
**Threshold concept.** Pre-training is one loop: sample a batch of token windows, predict every next token at once, take an Adam step on the mean cross-entropy, repeat; every trick (schedules, clipping, mixed precision) exists to keep that loop stable and efficient.
**Steps.** (1) `getBatch(ids, blockSize, batchSize, rng)` → `x, y` shifted by one (the "predict every position" trick). (2) One training step: forward, `crossEntropy`, backward, `clipGradNorm`, `AdamW.step`, `zeroGrad`. (3) LR schedule: linear warmup then cosine to 10% (`cosineWithWarmup`); test values at step 0, warmup, end. (4) Evaluation on the validation split with `noGrad`, and `estimateLoss` averaging several batches. (5) The full `train(config)` runner with a callback per step; a sampling function that decodes with the tokenizer.
**Concept must cover.** Why AdamW (per-parameter scaling; decoupled weight decay); why warmup (Adam's early variance estimates are bad); why clip; batch size in tokens (GPT-3 trained on 3.2M-token batches); tokens vs epochs (LLMs see most data once); what the loss means (loss 1.0 nats/char); overfitting vs undertrained; the "loss goes down" plot as the heartbeat of every lab; briefly: mixed precision, gradient checkpointing, checkpoint/resume.
**Demo.** Train the tiny GPT for ~300 steps on the char-level corpus (must finish < 60 s in Node; choose tiny dims, e.g. 2 layers, 32 dims, block 32, batch 16) with progress; plot train/val loss; print samples at step 0, mid, end; report tokens/sec and final loss.
**Honesty.** No mixed precision, no distributed anything (module 24), no data loader sharding (module 09).
**Lib.** `lib/gpt.js`, `lib/tensor.js`, `lib/optim.js`, `lib/tokenizer.js`, `lib/data.js`, `lib/util.js`.

## 08-scaling — Scaling laws & the arithmetic of compute
**Artifact.** A `planRun({params, tokens, gpus, gpuFlops, mfu, precision})` that returns FLOPs (6ND), wall-clock, memory (weights/grads/optimizer/activations), plus `chinchillaOptimal(computeBudget)` and a `scalingLoss(N, D)` from the Chinchilla fit; charts of the trade-offs.
**Threshold concept.** Training compute ≈ 6 × parameters × tokens; for a fixed compute budget there is a best split between model size and data, and everything about a training run's cost follows from a few multiplications.
**Steps.** (1) `trainingFlops(N, D) = 6·N·D` with a derivation (2 forward + 4 backward per parameter per token) and `inferenceFlops = 2·N` per token. (2) `wallClock(flops, gpus, peakFlops, mfu)`; realistic MFU 30–45%. (3) `trainingMemory(N, {precision, optimizer})`: weights 2 bytes (bf16), grads 2, Adam states 8 (fp32 m, v) + fp32 master 4 → ~16 bytes/param; activations scale with batch·seq·layers·hidden. (4) Chinchilla: `L(N,D) = E + A/N^α + B/D^β` with the paper's fit (E=1.69, A=406.4, B=410.7, α=0.34, β=0.28); `chinchillaOptimal(C)` finds N,D minimising L subject to 6ND=C (≈ 20 tokens per parameter). (5) An "over-training" analysis: Llama-3-8B trained on 15T tokens is far past Chinchilla-optimal because inference cost matters (compute the inference savings).
**Concept must cover.** Kaplan vs Hoffmann (Chinchilla); why 20 tokens/param; MFU; the GPT-3 (175B, 300B tokens, ~3.1e23 FLOPs) and Llama-3-70B/405B numbers as worked examples with "approximately"; H100 ≈ 989 TFLOP/s dense bf16 (NVIDIA datasheet) and 80 GB HBM3; GPU-hours to dollars at a stated assumed price; why memory, not FLOPs, forces multi-GPU (module 24).
**Demo.** Table for 4 famous runs; plot loss vs N at fixed compute (the U-shape); plot memory per parameter by precision/optimizer; done with the estimated H100-days for a chosen run.
**Lib.** `lib/util.js` only.

## 09-data-pipeline — The pre-training data pipeline
**Artifact.** A pipeline `runPipeline(docs, config)` with stages: language/quality heuristics (length, symbol ratio, repeated lines, boilerplate), exact dedup by hash, near-dedup by MinHash over shingles with Jaccard threshold, domain mixing by weights with epoch limits, tokenisation and sharding into fixed-size token shards with an index; a report table of what each stage removed.
**Threshold concept.** Model quality is decided as much by what you remove from the corpus as by what you keep: filtering, deduplication and mixing are modelling decisions, and every one of them is a measurable count.
**Steps.** (1) Quality filters as pure predicates with a reason string (Gopher-style rules: 50–100k words, mean word length 3–10, symbol-to-word ratio, ≥ 30% lines ending in terminal punctuation is a signal, "lorem ipsum"). (2) Exact dedup with `hash32` of normalised text. (3) MinHash: shingles of 5 words, k=32 hash functions from seeded linear hashes, estimated Jaccard, threshold 0.8; verify estimate vs exact Jaccard on a pair. (4) Mixing: sample documents by domain weights, cap epochs per domain (repeat penalty), report the effective tokens per domain. (5) Tokenise with the lab BPE, pack into shards of N tokens with EOS separators, write an index `{shard, offset, docId}`.
**Concept must cover.** C4/Gopher/RefinedWeb/FineWeb/DCLM-style filtering; why dedup matters (memorisation, loss on repeated data, Lee et al. 2021); MinHash-LSH at scale; data mixing (Pile weights, DoReMi); "epochs" for scarce high-quality data (Muennighoff et al. 2023: up to ~4 epochs is fine); contamination with evals; tokenisation at scale is embarrassingly parallel (sharded jobs).
**Demo.** Feed ~60 synthetic docs (some duplicates, some near-duplicates, some junk) plus `PROSE`; bar chart of docs removed per stage; table of the near-duplicate pairs found with Jaccard; final token count per domain; done with counts.
**Lib.** `lib/util.js` (`hash32`, `rng`), `lib/tokenizer.js`, `lib/data.js`.

## 10-sft — Supervised fine-tuning
**Artifact.** Chat template rendering (`<|user|>…<|end|><|assistant|>…<|end|>`), an SFT dataset builder that produces `x, y, mask` with the loss masked to assistant tokens only, packing of multiple examples into one sequence, a masked cross-entropy, and a fine-tune of the checkpoint on `INSTRUCTIONS`; before/after generations.
**Threshold concept.** SFT is pre-training on a different distribution with a mask: the model learns to continue *from the assistant's turn*, and what you mask (the prompt) decides what it learns to imitate.
**Steps.** (1) `formatChat(messages)` with the lab's `CHAT` markers, tokenised with special tokens. (2) `buildExample(tokenizer, prompt, response)` → `x, y, mask` where mask is 1 only on assistant tokens (including the end marker), 0 on prompt tokens. (3) `maskedCrossEntropy(logits, y, mask)` = sum(mask·nll)/sum(mask); test that changing prompt tokens' logits does not change the loss. (4) Packing several examples into `blockSize` with EOS separators and a mask that never crosses boundaries. (5) The fine-tune loop reusing module 07's step on the loaded checkpoint (lower LR, few hundred steps), with a generation before/after.
**Concept must cover.** Why instruction data changes behaviour with few examples (the base model already knows the language); loss masking rationale; chat templates in real systems (Llama 3's `<|start_header_id|>`, ChatML); packing and why attention should not cross packed examples (and that many libraries simply let it); learning rate 10× lower than pre-training; catastrophic forgetting; LoRA in one paragraph (rank-r adapters, and why it cuts optimizer memory) as a stretch.
**Demo.** Load `tiny-gpt.json`, show a prompt's raw completion before SFT, run SFT for ~200 steps (< 60 s), show the completion after with the chat template followed; plot masked loss; done with loss before/after.
**Lib.** `lib/gpt.js`, `lib/tensor.js`, `lib/optim.js`, `lib/tokenizer.js`, `lib/data.js` (INSTRUCTIONS, CHAT, formatChat), `lib/infer.js`/`lib/sampling.js` for generation.

## 11-preference — Reward models & DPO
**Artifact.** `bradleyTerryLoss(rChosen, rRejected)`, a tiny reward model head on the GPT's final hidden state, `dpoLoss(logpChosenPolicy, logpRejectedPolicy, logpChosenRef, logpRejectedRef, beta)` with implicit reward margins, sequence log-prob computation, and a training run on `PREFERENCES` that raises the margin.
**Threshold concept.** A preference between two answers is a training signal: the Bradley–Terry model turns "A beats B" into a logistic loss on a score difference, and DPO shows the policy's own log-ratios can play the role of that score, so no separate reward model is needed.
**Steps.** (1) Bradley–Terry: `-log σ(r_c − r_r)`; tests on hand values; gradient sign. (2) Sequence log-prob of a response given a prompt (sum of token log-probs over response tokens only, using the mask from module 10). (3) DPO loss `-log σ(β[(π_c − ref_c) − (π_r − ref_r)])`; test against hand-computed values; show it reduces to BT with implicit reward `β·log(π/ref)`. (4) Reward-model head: `Linear(C, 1)` on the last token's hidden state; train BT on the pairs. (5) DPO training loop with a frozen reference copy (`noGrad`), reporting the margin and reward accuracy (fraction of pairs where chosen > rejected).
**Concept must cover.** RLHF pipeline (InstructGPT: SFT → RM → PPO); why the reference model and β (KL control); DPO derivation sketch (the optimal policy under KL-regularised reward is `ref·exp(r/β)/Z`, invert for r); reward hacking and length bias; variants in one paragraph (IPO, KTO, ORPO, SimPO); what "reward accuracy 70%" means; that Llama 3 and many labs use DPO or similar in the loop.
**Demo.** Compute margins before training, train DPO for ~150 steps on the tiny model (< 60 s), plot margin and loss, table of a few pairs with before/after log-ratios; done with margin numbers.
**Lib.** `lib/gpt.js`, `lib/tensor.js`, `lib/optim.js`, `lib/tokenizer.js`, `lib/data.js` (PREFERENCES), `lib/checkpoints`.

## 12-rlvr — RL with verifiable rewards (GRPO)
**Artifact.** A GRPO trainer on a toy verifiable environment: prompts are one-step arithmetic questions (`MATH_TASKS`), the policy is the tiny GPT (or a small softmax policy over answer tokens if the GPT is too slow), rewards are exact-match, advantages are group-normalised, the loss is the clipped policy-gradient objective with a KL penalty to the reference; accuracy rises over training.
**Threshold concept.** When correctness can be checked by a program, you can train directly on "was it right": sample several attempts per prompt, reward the correct ones, and push probability toward them relative to their siblings; no learned reward model, no value network.
**Steps.** (1) The environment: `verify(question, completion)` returns 1/0 with tolerant parsing of the number; `rollout(policy, prompt, G, rng)` samples G completions. (2) Group-relative advantages `(r − mean)/ (std + eps)` per prompt; test that all-equal rewards give zero advantage (why GRPO wastes those prompts). (3) The policy-gradient loss on token log-probs: `-mean(A · logπ)` (REINFORCE) and then the PPO-style clipped ratio with `old` log-probs. (4) KL penalty to the reference policy (the unbiased k3 estimator `exp(ref−π) − (ref−π) − 1`). (5) The training loop; accuracy and mean reward per iteration; entropy tracking.
**Concept must cover.** RLHF with PPO vs RLVR; GRPO (DeepSeekMath, DeepSeek-R1) removing the critic; why group normalisation works as a baseline; reward hacking is impossible only if the verifier is sound (format rewards, length); test-time scaling / reasoning traces in one paragraph; asynchrony and rollout engines (vLLM inside the RL loop) as a systems note; the toy uses a tiny model, so improvements are modest but measurable.
**Demo.** Baseline accuracy on 30 tasks; ~40 GRPO iterations with G=8 (< 60 s; scale the policy accordingly, a softmax policy over a small answer vocabulary conditioned on hashed features is acceptable if the GPT is too slow, but say so); plot accuracy and KL; done with before/after accuracy.
**Lib.** `lib/data.js` (MATH_TASKS), `lib/tensor.js`, `lib/optim.js`, `lib/util.js`, optionally `lib/gpt.js`.

## 13-evals — An eval harness
**Artifact.** `runEval({tasks, model, grader, k})` with exact-match and regex graders, an LLM-as-judge grader with a scripted judge, the unbiased `passAtK(n, c, k)` estimator, bootstrap confidence intervals, contamination check by n-gram overlap, and a report table.
**Threshold concept.** An eval is a measurement instrument: its grader, its sample size and its contamination determine what the number means far more than the number itself does.
**Steps.** (1) Graders as pure functions with normalisation (case, whitespace, trailing period, number formatting). (2) `passAtK(n, c, k) = 1 − C(n−c, k)/C(n, k)` computed stably in log space (Chen et al. 2021); tests vs brute force. (3) Bootstrap CI: resample task scores B=1000 times with a seeded RNG; test the interval narrows with more tasks. (4) Judge grader: scripted `judge(question, answer, reference)` returning a verdict, plus agreement rate against exact-match; position-bias check by swapping. (5) Contamination: 13-gram overlap between eval prompts and a "training corpus"; the runner assembling everything into a report.
**Concept must cover.** Benchmarks (MMLU, GSM8K, HumanEval, SWE-bench) and what each measures; pass@k vs pass^k; variance from sampling temperature; prompt sensitivity; contamination (Sainz et al.); judge biases (verbosity, position, self-preference); why reporting CIs matters (Miller 2024, "Adding error bars to evals"); the harness is code, so version it with the model.
**Demo.** A scripted "model" with a per-task success rate; run 10 samples per task; table of pass@1/5/10 with CIs; bar of grader agreement; done with numbers.
**Lib.** `lib/util.js`, `lib/data.js` (MATH_TASKS).

## 14-decoding — Decoding & sampling
**Artifact.** A logit-processor pipeline: temperature, top-k, top-p (nucleus), min-p, repetition penalty, frequency/presence penalties, stop sequences; `sample(logits, opts, rng)`; a `generate` that runs the pipeline on the checkpoint via `lib/infer.js`; empirical distribution tests.
**Threshold concept.** The model outputs a distribution, not a token; decoding is a separate, controllable policy over that distribution, and each knob is a different way of cutting off the tail.
**Steps.** (1) Softmax with temperature and greedy; test that T→0 is argmax and T→∞ is uniform. (2) Top-k: keep the k largest logits, set the rest to −∞. (3) Top-p: sort, cumulative sum, keep the smallest set with mass ≥ p (always keep ≥ 1). (4) Min-p and repetition penalty (CTRL-style: divide positive logits by penalty, multiply negative) plus frequency/presence penalties (OpenAI-style additive). (5) Sampling with a seeded RNG and an empirical test: 20,000 draws match the filtered distribution within tolerance; stop sequences and max tokens in `generate`.
**Concept must cover.** Why greedy degenerates (repetition; Holtzman et al. 2019); the tail of the distribution is where errors live; temperature as a sharpening operator; top-p vs top-k behaviour on flat vs peaked distributions; min-p (2024) rationale; beam search and why chat models rarely use it; order of processors matters (penalties before temperature before truncation, as in HF `LogitsProcessor` lists); seeds and determinism across batch sizes (why "same seed, different output" happens in production).
**Demo.** Load `tiny-gpt.json`; show the top-10 distribution for one prompt as bars under four settings; generate 60 tokens with each setting; table; done with the entropy under each setting.
**Lib.** `lib/infer.js`, `lib/tokenizer.js`, `lib/checkpoints/*`, `lib/util.js`. Solution mirrors `lib/sampling.js`.

## 15-kv-cache — The KV cache
**Artifact.** Incremental decoding on the raw-tensor inference model: `newCache`, `forwardStep(model, cache, id)` appending K and V per layer, `prefill`, a FLOP counter, and a test that cached generation reproduces uncached generation token for token; measured speedup.
**Threshold concept.** In causal attention, past tokens' keys and values never change, so store them once and each new token costs one query against the cache instead of a full recompute; the price is memory that grows with context.
**Steps.** (1) Uncached `forward(model, ids)` → logits for every position (given as a worked example or in the starter); a helper that runs one block for a single position given full K/V. (2) The cache data structure: per layer `K, V` of shape `[H, T, dh]` grown by appending (a `Float32Array` with capacity doubling or simply concat); `newCache`. (3) `forwardStep`: embed the token at position `t = cache.length`, for each layer compute q,k,v for one position, append k,v, attend over the cache, MLP, and return logits. (4) `prefill` by looping steps (then note real systems batch it); equivalence test against `forward` at every position (tolerance 1e-4). (5) FLOPs per token with and without cache (`2N + 4·L·T·C` vs `T·(2N) + …`), memory of the cache `2·L·H·dh·T·bytes`; benchmark 64 tokens both ways.
**Concept must cover.** Prefill vs decode phases and why decode is memory-bound (sets up modules 16, 23); KV cache size arithmetic for a real model (Llama-3-8B: 32 layers, 8 KV heads (GQA), 128 head dim, 2 bytes → 128 KB per token, 16 GB at 128k context); GQA/MQA as cache reduction; why context length costs memory linearly and prefill compute quadratically; where paged attention (module 16) and prefix caching (module 17) come from.
**Demo.** Generate 64 tokens from the checkpoint with and without cache; plot per-token latency for both; heatmap of cache size vs context; done with speedup and equality confirmation.
**Honesty.** Batch size 1, no paging, float32.
**Lib.** `lib/infer.js` (reference `forward`; the learner writes the cache), `lib/checkpoints/*`, `lib/tokenizer.js`, `lib/sampling.js`.

## 16-batching — Continuous batching & paged attention
**Artifact.** A discrete-event simulator: requests arrive with prompt/output lengths; a scheduler admits requests per iteration subject to a KV-block budget; a paged block allocator with block tables and free lists; metrics: throughput (tokens/s), TTFT, TPOT/ITL, fragmentation; comparison of static batching vs continuous batching vs continuous + paging.
**Threshold concept.** A serving engine is a scheduler: at every decode iteration it decides which requests share the GPU, and paging the KV cache in fixed blocks is what lets it pack the memory tightly enough to keep the batch large.
**Steps.** (1) Request and iteration model: an iteration costs `t_fixed + t_per_token·(tokens in batch)` (the memory-bound decode approximation); static batching waits for the whole batch to finish. (2) Continuous batching: admit new requests when slots free up, evict finished ones every iteration; test throughput improvement on a skewed length distribution. (3) The block allocator: `blockSize=16`, `allocate(n)`, `free`, `blockTable` per request; internal fragmentation measured as wasted slots in last blocks. (4) Admission control by free blocks; pre-emption by recompute when out of memory. ## 30-lora — Parameter-efficient fine-tuning (LoRA)
**Artifact.** A `LoRALinear` wrapper on `lib/gpt.js`'s `Linear`: frozen base weight `W`, trainable low-rank `A` (r×in, Gaussian) and `B` (out×r, zeros) with scaling `alpha/r`; `applyLora(model, {rank, alpha, targets})` that wraps chosen projections (attention qkv/proj, MLP) in the module-06 GPT; a `merge()` that folds `W + (alpha/r)·B·A` back into a plain `Linear`; a memory accounting function for trainable parameters and optimizer state; an SFT run with LoRA compared with full fine-tuning on the checkpoint.
**Threshold concept.** Fine-tuning updates live in a low-rank subspace, so training a few percent of the parameters (and none of the optimizer state for the rest) recovers most of full fine-tuning, and the adapter can be merged away at inference for free.
**Steps.** (1) `LoRALinear.forward(x) = x·W + (alpha/r)·(x·Aᵀ)·Bᵀ`; with `B = 0` at init the wrapped layer equals the base layer exactly (test). (2) Gradients flow only to `A` and `B`: the base weight's `requiresGrad` is false; test that after a step `W` is unchanged and `A`, `B` moved. (3) `applyLora` on the GPT by target names from `paramNames`; count trainable vs total parameters; test the percentage for r=4 on the lab config. (4) `merge()`: fold the adapter into `W`; test logits identical before and after the merge (within 1e-5) and that the merged model has no adapter parameters. (5) Fine-tune on `INSTRUCTIONS` with LoRA (r=8) vs full fine-tuning for the same steps; report loss, trainable parameter count, and training-state memory (about 16 bytes per trainable parameter in bf16 mixed precision with AdamW, as in module 08; 8 of them are the two fp32 moments).
**Concept must cover.** Hu et al. 2021 (LoRA); why rank is enough (intrinsic dimension, Aghajanyan et al. 2020); alpha/r scaling; which matrices to target (attention vs MLP, QLoRA's "all linear layers"); QLoRA (Dettmers et al. 2023: 4-bit NF4 base + LoRA, paged optimizers) in one paragraph (a forward pointer: module 19 builds the quantisers; explain NF4 in one sentence here); adapters for multi-tenant serving (LoRA multiplexing, S-LoRA/Punica; a forward pointer to module 26); DoRA/rsLoRA as variants in one sentence; honesty: no quantised base here, tiny model, so the quality gap between LoRA and full FT is small.
**Demo.** Train LoRA r=8 and full FT for ~150 steps each (< 60 s total); plot both losses; bar of trainable parameters and training-state bytes; table of generations before/after; done with the parameter percentage and final losses.
**Lib.** `lib/gpt.js`, `lib/tensor.js`, `lib/optim.js`, `lib/tokenizer.js`, `lib/data.js`, `lib/checkpoints/*`, `lib/util.js`.

## 31-distillation — Knowledge distillation
**Artifact.** A distillation trainer: teacher = the lab checkpoint (frozen), student = a smaller GPT (1 layer, 32 dims); `softTargets(logits, T)`, `klDistillLoss(studentLogits, teacherLogits, T)` (forward KL with `T²` scaling), a mixed objective `alpha·KL + (1−alpha)·CE`, sequence-level distillation (train on teacher-generated text) and on-policy distillation (student samples, teacher scores each token), with a comparison of student trained from scratch vs distilled at equal steps.
**Threshold concept.** A teacher's full next-token distribution carries far more information per token than the single correct label; matching it lets a smaller student learn faster and closer to the teacher than training on the data alone.
**Steps.** (1) Temperature-softened targets: `softmax(z/T)`; test that T=1 is plain softmax and T→∞ is uniform. (2) Distillation loss: `T² · KL(p_teacher ‖ p_student)` averaged over positions; test against a hand-computed 3-class example and that the loss is 0 when logits match. (3) Mixed objective with the hard-label cross-entropy and an `alpha` knob; test the two limits. (4) Sequence-level distillation: generate a synthetic corpus from the teacher with `lib/sampling.generate` (temperature sampling as in module 07's `sample`), train the student on it; on-policy: sample from the student and score with teacher log-probs (reverse-KL flavour); implement both data paths. (5) The experiment runner: from-scratch vs distilled student at equal steps; report validation loss and agreement (top-1 match rate with the teacher).
**Concept must cover.** Hinton et al. 2015 (dark knowledge, temperature); Kim & Rush 2016 (sequence-level KD); on-policy / GKD (Agarwal et al. 2023) and why forward vs reverse KL matter (mode-covering vs mode-seeking); DistilBERT/TinyLlama/MiniLM as examples; distillation from API teachers via generated data (the "synthetic data" pipeline, linking to module 09); speculative decoding's draft models are often distilled students (a forward pointer: module 18 uses draft models); honesty: teacher and student are both tiny here.
**Demo.** Train both students ~200 steps (< 60 s); plot losses; bar of top-1 agreement with the teacher; table of sample generations; done with the gap in validation loss.
**Lib.** `lib/gpt.js`, `lib/tensor.js`, `lib/optim.js`, `lib/infer.js`, `lib/sampling.js`, `lib/tokenizer.js`, `lib/data.js`, `lib/checkpoints/*`, `lib/util.js`.

## 32-multimodal — Vision tokens: a tiny multimodal model
**Artifact.** A patch embedder that turns a small grayscale image (16×16, procedurally generated shapes) into a sequence of patch tokens (`patchify` → linear projection + learned position), a projector into the GPT's embedding space, an interleaved sequence `[image tokens] + [text tokens]`, a training loop that teaches the module-06 GPT to caption the shape ("a square", "a circle at the top"), and a `caption(image)` function; plus a minimal CLIP-style contrastive head (image embedding vs caption embedding with a symmetric InfoNCE loss) to show the alignment idea.
**Threshold concept.** A language model does not care where tokens come from: any modality becomes a sequence of vectors in the same embedding space, so "seeing" is a projection problem plus training data that pairs the two.
**Steps.** (1) `patchify(image, patch)` → `[nPatches, patch²]`; test shapes and that patches tile the image exactly. (2) Patch embedding: linear projection + position embedding to `[nPatches, C]`; test gradient flow. (3) Interleaving with text tokens and a loss mask that only trains on caption tokens, built here from scratch (`mask[t] = 1` only for caption positions); test the mask. Module 10, later in the path, generalises the same idea to assistant-only masking in chat data. (4) Contrastive head: image and caption pooled embeddings, symmetric cross-entropy over a batch (InfoNCE) with a temperature; test on a hand-made batch that the diagonal wins after training a few steps. (5) The caption trainer and `caption()`; accuracy on held-out synthetic images.
**Concept must cover.** ViT patches (Dosovitskiy et al. 2020); CLIP (Radford et al. 2021) contrastive alignment; LLaVA-style projector (a vision encoder + an MLP projector + an LLM) as the dominant recipe; early fusion vs late fusion; image tokens as a cost (a 1024×1024 image is hundreds to thousands of tokens; a forward pointer: modules 15 and 21 turn those tokens into KV-cache bytes and context budget); the honesty paragraph: 16×16 synthetic shapes and a two-layer GPT, no pretrained vision encoder. Recall questions may only cite modules 00–09 and 28, the modules that come before 32 in the recommended order.
**Demo.** Generate 200 synthetic shape images with captions, train ~200 steps (< 60 s), plot loss and caption accuracy, heatmap of one image's patch grid next to its tokens, table of captions for 6 held-out images; done with accuracy.
**Lib.** `lib/gpt.js`, `lib/tensor.js`, `lib/optim.js`, `lib/tokenizer.js`, `lib/data.js`, `lib/util.js`.

## 33-long-context — Long-context evaluation
**Artifact.** An eval suite for context length: a needle-in-a-haystack generator (a fact planted at a controlled depth in filler text), multi-needle and key-value retrieval variants (RULER-style), a `contextEval(model, {lengths, depths})` runner that reports accuracy per (length, depth) as a heatmap, an "effective context" estimator (the longest length at which accuracy stays above a threshold), and a token-cost model of long prompts (prefill FLOPs and KV bytes per length); run on a synthetic "model" with a configurable attention-fade so the mechanics are testable, and on the lab checkpoint within its 64-token window.
**Threshold concept.** A model's advertised context window and its effective context are different numbers; only a controlled retrieval test at many lengths and depths tells you where a model stops being able to use what you gave it.
**Steps.** (1) Haystack generator: filler text from the corpus, a needle sentence inserted at a fractional depth, a question; test that the needle lands within one sentence of the requested depth and the filler has no accidental needle. (2) Graders for exact and fuzzy retrieval (module 13's normalisation). (3) The runner over a grid of lengths × depths with `n` trials each and bootstrap CIs; test the shape of the result and determinism. (4) Effective-context estimate and the "lost in the middle" curve (accuracy vs depth at a fixed length); test on the synthetic model that fades attention with distance. (5) Cost model: prefill FLOPs and KV-cache bytes vs length for Llama-3-8B-like dims (module 15 formulas); the report.
**Concept must cover.** Needle-in-a-haystack (Kamradt 2023), RULER (Hsieh et al. 2024), "Lost in the Middle" (Liu et al. 2023), LongBench/InfiniteBench in one sentence; why long-context claims need retrieval, aggregation and reasoning tests, not perplexity; the role of RoPE scaling (module 29) and of attention sinks; the price of long prompts (module 17 caching, module 15 prefill compute; module 23's roofline as a forward pointer); honesty: the lab model's window is 64 tokens, so the synthetic fading model is what shows the curves.
**Demo.** Heatmap of accuracy over 6 lengths × 5 depths for the synthetic model; line of accuracy vs depth; bar of prefill FLOPs and KV bytes per length; done with the effective context estimate.
**Lib.** `lib/data.js`, `lib/tokenizer.js`, `lib/infer.js`, `lib/sampling.js`, `lib/checkpoints/*`, `lib/util.js`.

## 34-test-time-compute — Reasoning & test-time compute
**Artifact.** A test-time-compute toolkit on a synthetic multi-step reasoning task with a program verifier: `makeChains(n, seed)` generates arithmetic chains of 3–6 steps whose intermediate values are checkable; a scripted reasoner `sampleTrace(chain, next)` that errs at each step with a per-chain probability and carries the error forward, returning the steps and a final answer; `majorityVote(answers)` (self-consistency) and `weightedVote(answers, scores)`; `bestOfN(traces, scorer)` with three scorers — the oracle verifier (module 12's `verify`), a noisy outcome reward model (ORM) whose score is `correct + λ·spurious(trace) + noise` with a spurious preference for longer traces, and a process reward model (PRM) that scores each step and aggregates by the minimum; `stepBeamSearch({ beamWidth, expand, prm })` that extends partial traces one step at a time and keeps the best-scoring prefixes; `withBudget(trace, maxTokens)` that truncates a trace and forces an answer; and `ttcCost(strategy, config)` that turns samples × trace length into decode steps, peak KV-cache bytes and GPU-seconds with module 15's cache formula and module 16's `tFixed + tokens·tPerToken` iteration model.
**Threshold concept.** Once a model sometimes solves a problem, sampling more and choosing better turns inference compute into accuracy, and the selector sets the ceiling: majority vote converges to the model's most common answer, best-of-N against a learned reward model eventually picks the reward model's favourite mistakes, and only a sound verifier tracks pass@k.
**Steps.** (1) The task and the reasoner: chains with checkable intermediate values, per-chain step-error rates drawn so chains range from easy to hard, and deterministic wrong turns so wrong answers cluster; test that per-sample accuracy matches `(1 − e)^steps` within tolerance. (2) Self-consistency: `majorityVote` with a deterministic tie-break; accuracy vs N; test on hand-made answer lists, and that a chain whose most common wrong answer outnumbers the right one gets *worse* as N grows. (3) Best-of-N: `bestOfN` and `weightedVote`; test that with the oracle, choosing N traces from a pool of `n` samples of which `c` are correct, the expected accuracy equals module 13's `passAtK(n, c, N)`, and that with the default ORM (seeded) accuracy peaks and then falls as N grows (reward-model overoptimisation). (4) Process supervision: a PRM that scores each step (the step-level oracle with noise), `stepBeamSearch`; test that on 6-step chains with a noise-free PRM, beam search at an equal number of sampled tokens beats best-of-N. (5) Budgets and cost: `withBudget`, and `ttcCost` in decode steps, KV bytes and GPU-seconds at Llama-3-8B-like dims; the accuracy-vs-GPU-seconds frontier across strategies; test the cost arithmetic by hand against modules 15 and 16.
**Concept must cover.** Test-time compute as a second scaling axis next to training compute (Snell et al. 2024; OpenAI o1, 2024, and DeepSeek-R1, 2025, as the models that made long reasoning traces standard); self-consistency (Wang et al. 2022); verifiers and best-of-N (Cobbe et al. 2021); outcome vs process reward models (Uesato et al. 2022; Lightman et al. 2023, "Let's Verify Step by Step", PRM800K); reward-model overoptimisation (Gao et al. 2022); step-level search and why tree search such as MCTS has so far paid off less for LLMs than for games (the R1 report lists PRMs and MCTS among its unsuccessful attempts); budget forcing and thinking budgets (s1, Muennighoff et al. 2025; "reasoning effort" and thinking-token limits in APIs); parallel (sample many) vs sequential (think longer) compute; the serving cost of long traces: thousands of decode tokens per answer, a KV cache that grows with the trace (module 15), memory-bound decode steps (modules 15 and 16), and why reasoning tokens are billed as output tokens; how RLVR (module 12) grows the traces and how pass@k (module 13) is the ceiling a perfect selector reaches; honesty: the reasoner is scripted, not a trained model, so the curves show the mechanics of selection and their cost, not any real model's numbers.
**Demo.** 300 chains of 3–6 steps; accuracy vs N (1…64, log x) for majority vote, best-of-N with the ORM, best-of-N with the oracle and PRM beam search at matched token counts; accuracy vs GPU-seconds from `ttcCost`; bar of accuracy per strategy at a fixed budget; table of tokens, peak KV bytes and cost per strategy; done with the frontier and the N at which the ORM curve peaks.
**Lib.** `lib/util.js` (seeded RNG); the starter carries module 12's `verify`, module 13's `passAtK` and module 15's `cacheBytes` as given helpers, since modules may import only `lib/...`.

## 40-collectives — Collectives from scratch
**Artifact.** A tiny message-passing runtime (`World` of `n` simulated ranks, each with `send(to, buf)` / `recv(from)` over links with latency and bandwidth), and on top of it the NCCL collectives written by the learner: ring all-reduce (reduce-scatter + all-gather), tree all-reduce, hierarchical all-reduce (in-node then across-node), all-gather, reduce-scatter, and all-to-all; each verified for numerical correctness against a direct sum and timed on the simulated links.
**Threshold concept.** A collective is an algorithm, not a primitive: the same all-reduce can move very different amounts of data over very different links, and the right choice depends on message size, rank count and topology.
**Steps.** (1) The runtime: event queue, per-link serialization delay `bytes / bandwidth` plus latency `alpha`; test that one send of B bytes takes `alpha + B/beta`. (2) Ring all-reduce as reduce-scatter then all-gather over `n` chunks; test correctness for n = 2…16 and that each rank sends `2(n−1)/n · B` bytes. (3) Tree (binary / double binary) all-reduce; test that it beats the ring for small messages (latency-bound) and loses for large ones. (4) Hierarchical all-reduce on a two-level topology (fast in-node links, slow cross-node links); test that cross-node bytes drop by the node size. (5) All-to-all (MoE dispatch) with pairwise exchange; the timing report across algorithms, sizes and topologies.
**Concept must cover.** The alpha–beta model from module 24 as the lens; NCCL's ring and tree algorithms and protocol choices (LL, LL128, Simple) in one paragraph; bandwidth-optimal vs latency-optimal; in-network reduction (NVIDIA SHARP) as the next step; why collectives dominate step time at scale. Honesty: a discrete-event simulation of messages, not real transports; no congestion (that is module 41).
**Demo.** Animated `lab.graph` of chunks moving around a ring; plot of time vs message size for ring/tree/hierarchical (crossover visible); table of bytes per rank per algorithm; done with the crossover size.
**Lib.** `lib/util.js`; a new `lib/netsim.js` (event queue, links) is part of the groundwork to build first.

## 41-network-fabric — The data-center fabric
**Artifact.** A flow-level fabric simulator: topologies (2-tier leaf–spine fat-tree, rail-optimized 8-rail fabric, 3-D torus, and a rack-scale NVLink domain, NVL72-style, as the tier above the node), ECMP routing by hashing the flow 5-tuple, max-min fair bandwidth sharing between flows on each link, and a small packet-level mode for one switch (queue, ECN marking, a DCQCN-like rate controller) to show incast; used to run module 40's collectives and an MoE all-to-all on each topology.
**Threshold concept.** The network is a shared, contended resource: the collective's completion time is set by the most congested link and the slowest flow, so topology, routing and traffic pattern matter as much as raw link speed.
**Steps.** (1) Topology builders returning nodes, links and capacities; test bisection bandwidth of a fat-tree against the formula. (2) ECMP path choice by hash; test that two elephant flows collide on one uplink with the expected probability. (3) Max-min fair (progressive filling) rate allocation; test on hand-made examples. (4) Flow-level simulation of a collective: flows start, share, finish; measure completion time and tail on each topology; show the rail-optimized fabric keeping ring traffic on one switch tier. (5) Packet-level incast on one switch port with a finite buffer and ECN; show queue build-up and how rate control recovers.
**Concept must cover.** Fat-trees and oversubscription; rail-optimized designs for GPU clusters; InfiniBand vs RoCEv2 (RDMA over Ethernet), PFC and ECN/DCQCN; Meta's 2024 paper on RDMA over Ethernet for distributed AI training and the Llama 3 paper's cluster notes as case studies (figures hedged with "approximately"); Google's TPU torus with optical circuit switches; Ultra Ethernet as the direction of travel. Honesty: fluid flows, not packets, except the one-switch demo; small clusters (up to a few thousand endpoints) because it runs in a browser.
**Demo.** `lab.graph` of the fabric with link utilisation as stroke weight, animated over time; CDF of flow completion times per topology; bar of collective time per topology; done with the best topology and its margin.
**Lib.** `lib/netsim.js`, `lib/util.js`; module 40's collectives (reference copies in lib).

## 42-cluster-ops — Operating an AI cluster
**Artifact.** A cluster simulator with a job scheduler: jobs request GPU counts and a parallel layout, the scheduler does topology-aware gang placement (whole nodes, same rail group or pod), handles failures drawn from per-component rates, restarts from the last checkpoint, applies a power cap, and reports goodput (useful training time over GPU time), queueing delay and utilisation under different policies.
**Threshold concept.** At scale, the cluster's output is goodput, not peak FLOP/s: placement, failure recovery and checkpoint cadence decide how much of the hardware's time turns into training progress.
**Steps.** (1) Cluster inventory (nodes, GPUs, rails, pods) and a job model; test resource accounting. (2) Gang scheduling with topology-aware placement vs first-fit; test that a placement never splits a tensor-parallel group across nodes. (3) Failures and restarts: exponential failure times per GPU/NIC/host, lost work since the last checkpoint, restart delay; test expected lost work against the closed form. (4) Checkpoint cadence (Young/Daly optimum from module 25) and its interaction with checkpoint write bandwidth; test the optimum. (5) Power capping: a per-rack budget that throttles clocks, trading step time for more concurrent jobs; the goodput report across policies.
**Concept must cover.** Slurm and Kubernetes-style schedulers in one paragraph; gang scheduling and fragmentation; failure statistics at scale (the Llama 3 paper's interruption counts, hedged); asynchronous and in-memory checkpointing; hot spares; power and cooling limits (rack density, liquid cooling) as the real constraint on AI data centers. Honesty: a statistical simulator with made-up but plausible rates, clearly labelled.
**Demo.** Gantt-style timeline of jobs on nodes (a `lab.table`/heatmap until a timeline view exists); plot of goodput vs checkpoint interval; bar of goodput per scheduling policy; done with the best policy's goodput.
